# LanguageBot

Telegram-бот для персонального вивчення англійської мови: автоматично
генерує нові слова та вирази під рівень користувача (через Gemini AI),
підтримує активний пул із 50 слів, перевіряє засвоєння через квізи (а не
кнопку «Вивчено»), повторює слова за алгоритмом spaced repetition і будує
персональну карту знань користувача в Obsidian.

## Основні можливості

- Персональний активний пул до **50 слів/виразів** одночасно (нове слово
  автоматично додається замість вивченого).
- **6 типів питань**: EN→UA вибір, UA→EN вибір, заповнення пропуску, вибір
  слова для речення, переклад речення (вільний текст, оцінюється AI),
  вибір правильного прикладу вживання. Складність питання підбирається
  динамічно за кількістю успішних повторень слова.
- **Spaced repetition**, натхненний SM-2: базова прогресія 1 → 3 → 7 → 14
  днів; помилка відкидає слово на один крок назад і скорочує інтервал;
  засвоєним слово стає лише після повного циклу правильних відповідей
  («вгадати» неможливо).
- **Генерація слів через Gemini AI**, з ранжуванням по графу знань: нові
  слова спершу добираються серед синонімів/антонімів/колокацій уже відомих
  слів (і, якщо кандидатів більше, ніж треба, потужніша модель оцінює й
  ранжує їх), а лише потім — через генерацію з нуля. Словниковий каталог
  спільний для всіх користувачів і повторно використовується, щоб
  економити ліміт AI-запитів.
- **IPA-транскрипція** (британська/американська) для кожного слова.
- **Переклад і приклад ховаються під спойлер** у картці — видно одразу
  після відповіді, а не заздалегідь.
- **Персональна карта знань в Obsidian**: кожне слово стає нотаткою з
  посиланнями на синоніми/антоніми/колокації/тему.
- **Гнучкий розклад сесій** і **тихі години** (з урахуванням часового поясу
  користувача, визначеного за його локальним часом).
- **Налаштування** через `/settings`, **статистика** через `/stats`
  (вивчено всього/за тиждень/за місяць, кількість повторень, відсоток
  правильних відповідей, швидкість навчання, поточний рівень).

## Архітектура проєкту

```
bot/
├── handlers/       # тонкі aiogram-роутери: розбір апдейту → виклик сервісу → рендер
├── keyboards/       # inline/reply-клавіатури
├── states/          # aiogram FSM-стани (квіз-переклад, налаштування)
├── learning/         # ЧИСТИЙ домен: SRS-алгоритм, вибір типу питання, правила пулу/рівня
│                      # -- без залежностей від БД чи Telegram, повністю юніт-тестований
├── database/
│   ├── models/        # SQLAlchemy-моделі
│   └── repositories/  # доступ до БД (по одному репозиторію на модель/групу моделей)
├── services/         # бізнес-логіка/оркестрація (це той шар, який викликав би й web/mobile клієнт)
├── ai/               # AIProvider + Gemini-реалізація, роутинг моделей, rate limiter,
│                      # валідатори, prompts/ (по модулю на родину задач)
├── scheduling/       # APScheduler: контекст, задачі, тихі години
├── obsidian/          # генерація Markdown-нотаток і slug'ів для vault
├── rendering/         # рендер квіз-карток у Telegram HTML (спільний для ручного і push-режиму)
└── utils/             # логування, час/UTC-офсет

alembic/               # міграції БД
scripts/                # допоміжні скрипти (seed, backfill, smoke-тести AI)
tests/
├── unit/               # тести чистої логіки (learning/, obsidian/, utils/) -- без БД
└── integration/         # тести сервісів проти реальної PostgreSQL (тестова БД)
```

Ключовий принцип: **бізнес-логіка живе в `services/`, а не в `handlers/`**.
Алгоритм навчання (`learning/`) не залежить від Telegram чи БД, тож його
можна повторно використати з майбутнім web- або mobile-клієнтом без змін.
AI (`ai/`) лише пропонує дані — критичні правила (ліміт 50 слів, «вивчено»
тільки після правильної відповіді, без дублікатів, відповідність рівню)
контролюються кодом, а не довірою до відповіді моделі.

## Як працює навчання

### Активний пул (`PoolService`)

У кожного користувача одночасно щонайбільше **50** слів/виразів у статусах
`new` / `learning` / `review`. Коли слово переходить у статус `learned`,
`PoolService` автоматично підбирає заміну через `VocabularyGenerationService`.
Дедуплікація та перевірка рівня відбуваються в коді, незалежно від того, що
поверне AI.

### Spaced repetition (`bot/learning/srs_algorithm.py`)

Базова прогресія інтервалів для чотирьох перших правильних відповідей:
**1 → 3 → 7 → 14 днів**. Деталі:

- Кожна відповідь оновлює `ease_factor` за формулою у стилі SM-2 (quality
  4 для правильної відповіді, 2 для неправильної) — на практиці це означає,
  що `ease_factor` не росте на правильних відповідях, а лише падає на
  помилках (не нижче 1.3).
- **Правильна відповідь**: `repetitions += 1`; інтервал бере наступне
  значення з таблиці 1/3/7/14 (а після четвертого повторення продовжує
  рости через `ease_factor`). Слово переходить у `review`, коли інтервал
  досягає 7 днів, і в `learned` — лише якщо **одночасно**: `repetitions ≥ 4`,
  `consecutive_correct ≥ 4` і інтервал ≥ 14 днів.
- **Неправильна відповідь**: слово відкидається на один крок назад
  (`repetitions -= 1`, але не нижче 0), інтервал скорочується вдвічі
  (мінімум 0.5 дня), `consecutive_correct` обнуляється. Слово ніколи не
  повертається в статус `new`.

Це унеможливлює «вгадування»: одна помилка ламає серію правильних
відповідей і відкладає засвоєння.

### Вибір типу питання (`bot/learning/question_selector.py`)

Складність питання підбирається за кількістю повторень слова: чим більше
успішних повторень, тим складніший тип питання (від простого вибору
перекладу до вільного перекладу речення). Помилка тимчасово знижує
складність до найпростішого типу.

## Генерація слів через AI

`VocabularyGenerationService` — єдина точка, де AI впливає на словник
користувача. Порядок дій при поповненні пулу:

1. **Слова, суміжні в графі знань.** Синоніми/антоніми/колокації вже
   відомих слів (поле на кожному `Word`, тобто сам граф уже живе в
   PostgreSQL) шукаються серед ще не пов'язаних із користувачем слів
   каталогу. Якщо таких кандидатів більше, ніж треба — потужніша модель
   ранжує їх (`rank_next_word_candidates`, оцінка + обґрунтування); бізнес-
   логіка все одно приймає фінальне рішення й застосовує ті самі перевірки
   дублікатів/рівня, що й завжди.
2. **Будь-яке інше непов'язане слово каталогу відповідного рівня**, якщо
   кроку 1 не вистачило.
3. **Жива генерація через Gemini**, лише на решту (**один** запит із
   «запасом» — просимо трохи більше слів, ніж треба, щоб не робити
   повторний виклик після фільтрації).

Кожне запропоноване AI слово проходить валідацію (`bot/ai/validators.py`)
перед записом у БД: чи не дублікат, чи в межах допустимого рівня (не
більш ніж на один крок CEFR вище рівня користувача), чи приклад справді
використовує це слово, чи транскрипція схожа на валідний IPA (інакше поле
просто лишається порожнім, а не все слово відкидається).

Це свідоме рішення для економії безкоштовної квоти Gemini API (за
замовчуванням дуже обмежена — див. [Відомі обмеження](#відомі-обмеження)).

## AI Engine

`bot/ai/` — єдина точка доступу до Gemini API; жоден інший модуль не
імпортує `google.genai` напряму.

- **Дворівнева модель** (`bot/ai/router.py`, `bot/config.py`:
  `GEMINI_DEFAULT_MODEL` / `GEMINI_ADVANCED_MODEL`): прості задачі
  (переклад, IPA, приклади, вибір/перевірка відповіді) йдуть на дешеву
  `flash-lite`-модель; задачі, що вимагають справжнього аналізу графа
  знань (`SELECT_NEXT_WORD`, `ANALYZE_KNOWLEDGE_GRAPH`, `ANALYZE_PROGRESS`)
  — на повноцінну `flash`. Назви моделей ніде не хардкодяться, лише в
  конфігу. Якщо виклик на основній моделі остаточно провалюється —
  один раз пробуємо іншу модель-рівень як fallback.
- **Rate limiter** (`bot/ai/rate_limiter.py`): простий in-process
  rolling-window лічильник (без Redis/черги — для 1–2 користувачів це
  зайве), який не дає кільком викликам поспіль одразу вперлися у
  free-tier ліміт на хвилину.
- **Валідатори** (`bot/ai/validators.py`): перевіряють смисл відповіді AI
  (наприклад, чи приклад справді містить слово), а не лише структуру
  (структуру вже гарантує `response_schema`/pydantic).
- **Облік використання**: кожен виклик Gemini логується в таблицю
  `ai_requests` (тип задачі, модель, токени, затримка, статус) через
  власну коротку сесію БД усередині `GeminiAIProvider` — це єдиний
  навмисний виняток із правила «`bot/ai/` без сесії БД», оскільки це
  лише запис телеметрії, а не бізнес-рішення. Переглянути витрати:
  `python -m scripts.ai_usage_report --days 7` (спрощений аналог
  admin-дашборда — для 1–2 користувачів повноцінна адмін-панель
  не виправдана).
- **Фонове поповнення каталогу** (`bot/scheduling/catalog_topup.py`):
  раз на добу перевіряє, чи не порідшав каталог на якомусь рівні CEFR, і
  за потреби підтягує нову партію слів заздалегідь — щоб `PoolService` як
  можна частіше знаходив готове слово в каталозі й не чекав на живий
  виклик Gemini в момент, коли користувач відкрив бота.

## Персональна карта знань в Obsidian

Бот керує окремим Obsidian vault (тека `obsidian-vault/` у корені проєкту,
або шлях з `OBSIDIAN_VAULT_PATH`). Це **не** заміна основної БД — PostgreSQL
лишається джерелом істини для прогресу, статистики й розкладу. Vault —
лише зручне, візуальне дзеркало:

```
obsidian-vault/
└── users/<user_id>/
    ├── Words/<слово>.md    # переклад, транскрипція, статус, wiki-посилання
    └── Topics/<тема>.md     # автоматично оновлюваний список слів теми
```

Кожна нотатка слова містить `[[wiki-посилання]]` на синоніми, антоніми,
колокації й тему — навіть якщо відповідної нотатки ще немає (Obsidian
показує це як «незавершене» посилання, це нормально й навмисно: нове слово
не створюється автоматично лише через наявність зв'язку). Синхронізація
відбувається при кожній зміні статусу слова (`SpacedRepetitionService`) і
при додаванні слова в пул (`PoolService`).

Щоб переглянути граф: відкрий Obsidian → **Open folder as vault** → вкажи
`obsidian-vault` → іконка графа (`Ctrl+G`).

## Команди та меню бота

Прикріплена клавіатура:

- **📚 Вчити слова** — показує наступне слово (спершу ті, що чекають
  повторення, потім нові).
- **🔄 Повторення** — показує слово, яке саме зараз чекає на повторення за
  розкладом SRS (якщо такого немає — просить скористатись «Вчити слова»).

Команди (меню `/`):

- `/start` — реєстрація, вибір рівня (CEFR A1–C2), початкове наповнення
  пулу.
- `/settings` — рівень, кількість нових слів на день, розклад сесій, тихі
  години, часовий пояс.
- `/stats` — статистика (вивчено всього/за тиждень/за місяць, повторення,
  % правильних відповідей, швидкість навчання, поточний рівень).

## Планувальник і тихі години

`ScheduleService` реєструє в APScheduler по одному `CronTrigger` на кожну
сесію користувача (у його локальному часі). Задача (`SessionJobRunner`) під
час спрацювання **повторно перевіряє** тихі години на випадок, якщо
налаштування змінились після реєстрації — якщо зараз тихі години,
повідомлення переноситься на найближчий дозволений час, а не надсилається.

Часовий пояс визначається без списку IANA-назв: бот просто питає «котра
зараз у тебе година», порівнює з UTC і зберігає фіксоване зміщення (у
хвилинах). Це означає відсутність автоматичного врахування переходу на
літній/зимовий час — якщо зміщення «попливло», достатньо ще раз відповісти
на це питання в `/settings`.

## База даних

Основні таблиці (PostgreSQL, міграції — Alembic):

| Таблиця | Призначення |
|---|---|
| `users` | телеграм-користувач, рівень CEFR, статус онбордингу |
| `user_settings` | часовий пояс (як UTC-зміщення), тихі години, ціль нових слів/день |
| `words` | спільний словниковий каталог (лема, переклад, приклад, транскрипція, рівень, тема, синоніми/антоніми/колокації) |
| `user_words` | прогрес користувача по слову: статус, SRS-стан, кількість правильних/неправильних відповідей |
| `answer_history` | кожна спроба відповіді (для статистики й адаптивного алгоритму) |
| `learning_sessions` | налаштований розклад push-сесій (час доби) |
| `learning_session_runs` | лог кожного спрацювання задачі планувальника (sent/deferred/skipped) |
| `knowledge_nodes` | зв'язок між словом користувача і файлом нотатки в Obsidian |
| `ai_requests` | лог кожного виклику Gemini (тип задачі, модель, токени, затримка, статус) |

## Встановлення та запуск

### Docker Compose (рекомендовано)

1. Скопіюй `.env.example` у `.env` і заповни `BOT_TOKEN` та `GEMINI_API_KEY`.
2. `docker compose up -d` — підніме PostgreSQL і бота; міграції
   застосовуються автоматично при старті контейнера бота
   (`docker/entrypoint.sh`).
3. Vault буде доступний у `./obsidian-vault` на хості (bind mount).

### Локально (без Docker)

```bash
python -m venv .venv
.venv/Scripts/pip install -e ".[dev]"
# піднімається окрема PostgreSQL (наприклад через docker compose up -d postgres)
alembic upgrade head
python -m bot.main
```

## Розробка

```bash
pytest                        # весь набір тестів (unit + integration)
pytest tests/unit              # тільки чиста логіка, без БД
ruff check bot scripts tests   # лінтер
mypy bot                       # типізація
```

Інтеграційні тести використовують окрему базу `languagebot_test`
(створюється автоматично при першому запуску Postgres-контейнера, див.
`docker/init-test-db.sql`), щоб не зачіпати дані реального бота.

Допоміжні скрипти:

- `python -m scripts.seed_dev_words` — наповнює каталог стартовим набором
  слів (використовується і в тестах).
- `python -m scripts.manual_gemini_smoke` — ручна перевірка інтеграції з
  реальним Gemini API (генерація слів, речення, оцінка перекладу).
- `python -m scripts.backfill_transcriptions` — дозаповнює транскрипцію для
  слів, які її не мають, і оновлює відповідні нотатки в Obsidian.
- `python -m scripts.ai_usage_report --days 7` — зведення по витраті
  Gemini-квоти за період (кількість запитів/токенів по кожній моделі,
  останні помилки).

## Відомі обмеження

- **Безкоштовний тариф Gemini API обмежений.** За замовчуванням
  використовується `gemini-flash-lite-latest` — легша модель із суттєво
  вищим безкоштовним лімітом, ніж повноцінний `flash` (на повному `flash`
  ліміт міг падати аж до ~20 запитів/день). `VocabularyGenerationService`
  додатково економить квоту (спершу спільний каталог, потім один «щедрий»
  AI-запит замість кількох дрібних), але за дуже активного використання
  ліміт усе одно можна вичерпати — тоді пул тимчасово поповнюється
  повільніше, доки квота не скинеться (зазвичай щохвилини або щодня,
  залежно від типу ліміту).
- Розклад планувальника живе **лише в пам'яті процесу** (не в персистентному
  job store): при рестарті бота задачі повторно реєструються зі збережених
  `learning_sessions`, тож розклад не втрачається, але задача, що мала
  спрацювати саме під час рестарту, могла бути пропущена.
- **Ранжування наступного слова через граф знань реалізоване частково.**
  Кандидати беруться з синонімів/антонімів/колокацій уже відомих слів і
  ранжуються AI (`rank_next_word_candidates`) — але явне «знаходження
  прогалин» у графі (запропонувати слово, якого бракує між двома вже
  відомими темами) і генерація навчальних фраз із кількох відомих слів
  одночасно (`book a room`) поки не реалізовані окремо — це природне
  розширення поточного підходу, а не окрема підсистема.
